# 大规模路线（2026-09-30）

## 实测成本给出的上限

| 项 | 实测 | 来源 |
|---|---|---|
| 执行 | 约 4.5 µs / 非零权重（每条命令） | E1、T44K |
| 常驻内存 | 约 2.5 KB / 命令方块 | E4 |
| 常驻空转 | 约 0.1 µs / 命令方块 / tick（移出常加载区即停） | E4 |
| 换页（structure load 命令方块） | 约 52–110 µs / 方块 | E2、E3 |
| 普通方块加载 | 约 6.5 µs / 方块 | E3 |

- 三值 60% 为零时，每个参数约 0.4 条命令，**每 token 约 1.8 µs × 参数量**：1M ≈ 2 s，10M ≈ 20 s，0.1B ≈ 3 分钟，1B ≈ 30 分钟。
- **内存才是先撞上的墙**：常驻 100 万个命令方块约 2.5 GB。普通电脑能常驻约 200–300 万个，即约 **5–7M 参数**（60% 为零）。再往上必须换页或用方块 ROM，每个权重的成本变成 10–100 倍。

## 阶梯

1. **T1M**（本次）：d=128、8 头 × 16、FFN 384、6 层、词表 1024、上下文 32，**1,249,280 参数**（T44K 的 22 倍）。常驻，分 15 个阶段，每个阶段一条链、一个 tick，阶段之间接力。
2. **T5M 左右**：常驻的极限，验证内存和启动。
3. **更大**：需要新的存储路线。候选：普通方块 ROM + 固定"读取程序"（`/clone` 把权重块搬进读取窗口，读取程序用 `execute if block` 决定加减）；成本要先测（E5：`/clone` 每块多少 µs、`execute if block` 成立/不成立各多少 µs）。

## 引擎改动（已完成，离线通过）

- `spec.configure("t1m")`：模型尺寸改成可配置，T44K 仍是默认，**M6 世界的 52,764 个方块逐字节不变**（回归检查）。
- `Compiler(staged=True)` + `stages(budget)`：把一次前向切成若干条 ≤ 6 万条命令的链。只在"自成一体"的单元之间切（每个寄存器只由一个单元写），所以任何一条链被多执行一次都不影响结果：
  - embedding 分成 `ee = E[cur]`、`pp = P[pos]`、`xe = ee + pp` 三类单元；
  - 注意力掩码、ReLU 放进写同一寄存器的单元里；
  - LM head 分块求局部 argmax，最后按 token 顺序合并（并列时小 id 胜，和原来一致）；
  - **因果跳过**：注意力只算 j ≤ pos 的位置（门 + 条件块），平均省一半注意力命令。
- `layout.build_plan_staged`：每阶段一条脉冲链；链尾锁存 `stg == k` 后把 `stg` 推进、最后才给下一阶段通电。某条链被多触发一次时 `stg` 已经不等于 k，不会接力出第二条流水线。每 96 层换一列（每列一个常加载区），每区块约 2.4 万个命令方块。

## 验证（随机权重）

- T44K 尺寸强制切 7 段：离线 6 个提示词 96 次前向 0 不一致；世界模拟 当场 / 下一 tick / 重复触发 三种都 PASS，**每阶段 1 tick**。
- **T1M**：离线 1 个提示词 32 次前向，全部中间整数 0 不一致（两种除法语义），**每 token 平均 57.7 万条有效命令**；静态 88.2 万个命令方块（约 2.1 GB），3 列。
- 预计实机每 token 约 2.6–3 秒（15 个 tick）。

## 实机（2026-09-30，新超平坦世界）

- 88.2 万个命令方块（3 列 × 64 × 64），用调试桥 24 µs/块摆放（共约 21 秒）；63,062 个寄存器名全部试写通过；游戏进程私有内存约 4.6 GB。
- **提示词 1：连续 32 次前向，31 个生成 token 和最终状态 34 个整数全部和整数规范一致。**
- 速度：每 token 18.2–18.9 秒，每次前向 30–31 个 tick。
  - **空转**：88 万个刚放下的命令方块，空闲时每 tick 212 ms（约 0.24 µs/块，和 E4 刚放下时的 0.22 µs 一致）。
  - **接力延迟**：链尾 `setblock` 放红石块后，下一条脉冲链要 **2 个 tick** 后才执行（桥里放则是 2–4 个 tick）。所以每阶段 2 个 tick，每 token 付 30 次空转。
  - **每阶段的计算**：真实生成时每阶段 1.3–2.7 秒（每 2 个 tick），扣掉空转约 1 秒，相当于约 20 µs/条，是基准的 4 倍多。**未查明**：
    - 同样的阶段，如果输入和上次完全一样（寄存器被写回原值），每阶段只要约 0.25 秒（约 5 µs/条）；
    - 但单独的基准都复现不出变慢：数值每 tick 变化、±100 万来回跳、`execute if` 结果每 tick 翻转、记分项里 6.3 万个名字 vs 几个名字、两个不同名字的运算，全都是 4–6 µs/条。
- **`gamerule maxcommandchainlength` 可以调到 1,000,000**：一条 10 万个命令方块的链一次执行完（10 万条全部执行）。所以整个前向可以放进一条链、一个 tick 跑完，每 token 只付 1 次空转，而不是 30 次。
  - 已实现 `Compiler.single_staged()` + `layout.set_footprint(192)` + `build_plan_single(..., max_chain=1e6)`，T44K 尺寸的世界模拟（链头多跑 0/1/2 tick）PASS。
- **T1M 单链实机（新超平坦世界）**：874,671 个方块（192 × 63 × 73 层），摆放约 22 秒。
  - **提示词 1 再次逐整数通过**（31 个 token + 34 个整数）；**每 token 正好 1 个 tick**。
  - **每 token 12.8 秒**（分阶段版 18.9 秒）。空闲 197 ms/tick。
  - 冻结数值（控制不推进，每 tick 重算完全相同的值）仍要 **7.7 秒/tick**，约 9 µs/方块。所以长链里每条命令的实际成本是小基准（4–6 µs）的 2–4 倍，和"值是否变化"只有部分关系。**原因未查明**。下一步的对照实验：同一条简单命令分别放在 2 万 / 10 万 / 87 万长的链里计时，看是不是和链长有关。

## 慢因排查（2026-09-30 晚，GPT 深度研究之后）

- **TrackOutput=0：基本无效**。用 `SetBlockEntityData` 把 872,104 个命令方块的 TrackOutput 设为 0（并清空 LastOutput），同一个提示词整句平均 11.1 s/字（改之前 11.3 s），结果仍逐整数一致。GPT 报告的首要假设不成立。
  - **坑**：`SetBlockEntityData` 会按方块实体里的 `LPCommandMode / LPCondionalMode / LPRedstoneMode` 重设方块类型。用 `SetCommandBlock` 放下的方块这三个字段可能是 0，写回后变成"脉冲、无条件"，链从中间断掉。必须同时把这三个字段写成正确值（`MODE`、是否条件、自动=0 / 需红石=1），写完再核对方块名和 aux。
- **重新载入**：87 万块的世界进图后约 8 分钟才把区块读完，期间 SrvTime 半分钟才变一次。大批方块实体改动后，游戏持续写盘（每 15 秒 13–75 MB），期间调试桥连不上。
- **前缀二分**（真实 T1M 链，数值冻结，pos=32，每 tick 耗时）：

  | 截到 | 每 tick |
  |---|---|
  | 10 万 | 0.43 s |
  | 30 万 | 1.53 s |
  | 60 万 | 3.59 s |
  | 70.2 万（第 4 层结束） | 4.3 s |
  | 76.6 万（第 5 层注意力结束） | 5.4 s |
  | **79.5 万（+ 第 5 层 O 投影、RMSNorm、FFN 上投影）** | **22.4 s** |
  | 81.5 万（第 5 层结束） | 22.2 s |
  | 87.1 万（LM head 结束） | 23–26 s |

  **约 17 秒集中在 2.9 万个方块上**（约 600 µs/块）。同样结构的第 4 层完全正常。
- 把这 2.9 万块原样复制到测试区单独跑：**很快**（每 tick 和空闲几乎一样）。所以不是命令文本（排除了敏感词过滤器变慢），而是和"在一个 tick 里已经执行了多少 / 多久"有关的超线性效应。
- 旁证：5K 条 `execute as @a at @s run scoreboard …` 每 tick 0.34 s（68 µs/条），15K 条却要 18.5 s（1.25 ms/条）：条数 3 倍，时间约 54 倍，同样是超线性。
- 当前假设：**同一个 tick 里有某种随执行量累积的开销，过了某个点以后每条命令都变得极贵**。未确定累积的是什么（命令数、耗时、某类事件）。
- 实际意义：如果成立，**把一次前向拆成几段、每段放在不同的 tick 里跑**（每段都停在拐点以前）会比一个 tick 跑完快很多。之前分 15 段的版本也慢，但那时每段 2 tick、而且还有别的变量，需要按拐点重新设计再测。
- 下一步对照：同一种命令在一个 tick 里跑 5K / 7.5K / 10K / 12.5K / 15K 条，找出拐点和曲线形状；再用 T1M 拆成 2 段、每段一个 tick，直接测每字时间。

## 分段扫描（2026-09-30 晚，按 GPT 第二份报告的首要建议）

同一个训练版 T1M、同一个提示词（「中华」，32 字），新超平坦世界，`export_staged.py … sweep --budget N`（192 宽底面，每段一条链，链尾 `setblock` 红石块接力）：

| 版本 | 每段命令数 | 每字 | 每字 tick 数 | 结果 |
|---|---|---|---|---|
| 单链（对照，另一张图） | 87 万 | 11.1–11.3 s | 1 | 逐整数一致 |
| **2 段** | 44 万 / 43 万 | **16.6 s** | 4.1 | 逐整数一致 |
| **6 段** | 约 15 万 | **约 19.6 s**（空闲偏高，见下） | 12 | 前 10 字未见异常，提前停止 |

- 6 段版每段（2 个 tick）的耗时：G0 1.3 s，G1–G4 各 3.3–5.2 s，G5 1.9–2.4 s。当时空闲 760 ms/tick（刚摆完 87 万块，另一版本的区块可能还缓存着），扣掉空闲后每段 15 万条仍要约 2.8 s（约 19 µs/条）；单链里同一位置同样的命令（第 15–30 万块，数值冻结）只要约 1.1 s。
- **结论：分段接力不能消除退化，反而更慢**。和早前 15 段版本（18.9 s/字）的结果一致。GPT 报告"拆到多个 tick 就能回到拐点以下"的假设在这种接力方式下不成立；退化看起来会跨 tick 延续，或者和"真实数据流过"本身有关。
- 教训：不要在游戏运行中用 `/fill` 一次删除几十万个命令方块（87 万块时整个世界冻住 10 分钟以上，只能强退）。换版本时改为搭在新空地、移除旧的常加载区，或者用新世界。

## 根因排查：对照实验 C（2026-09-30 深夜）

新世界里把单链 T1M 摆在 x=33536，数值冻结（run=0，pos=32，cur=2），用"临时把第 s 块换成循环链头、在第 e 块截断"的办法只执行 [s, e)：

| 执行范围 | 每 tick（有测速定时器） |
|---|---|
| 探针单独（765,848 → 794,502） | 0.79 s（空闲约 0.42） |
| 第 5 层开头 → 探针结束 | 1.30 s |
| 第 4 层开头 → 探针结束 | 2.25 s |
| 链头 → 770K / 780K | 6.4 / 6.6 s |
| 链头 → 探针开头 | 6.4 s |
| **链头 → 探针结束** | **38.6 s** |
| embedding 之后（137,514）→ 探针结束 | 39 s |

- **探针本身不贵**，只有前面在同一个 tick 里已经执行了很久或很多时，最后 1.45 万块（第 5 层 FFN 上投影后半）才爆炸；跳过 embedding 的 13.7 万块（大多是被跳过的条件块）不影响。
- 进程内存在长 tick 里几乎不变（±30 MB），不是内存累积。
- **测量本身有影响**：同一配置（链头 → 探针结束）在不开任何定时器时，调试桥挂着、用每 tick 加 1 的命令方块计数是 **11.5 s/tick**，用户看 SrvTime 约 12000；开着 0.05 s 定时器时是 38 s。所以前面用定时器测出的断崖数值被放大了，断崖真实存在但幅度要以无定时器的数据为准。
- 零附加包对照没测成：链头通着电存档，移除附加包后进图两次都在加载快结束时闪退（推测是加载期间就开始跑 12 s 的长 tick）。

### 踩到的坑
- 用 ModSDK 把已有的连锁命令方块"原地改成"常开循环方块，它不会开始 tick（沿用了旧的方块实体）。必须先设成空气，再放循环命令方块，再 `SetCommandBlock`。通过 API 放的常开循环方块在世界重进后也可能不再运行（tick 计数器就停了）。
- 用 Python 加的常加载区在重进世界后可能丢失，要重新加，然后等约 8 分钟加载。
- **不要让链头通着电时存档**：重进时会在加载期间直接跑长 tick，导致闪退。零附加包测试要用"原版按钮给链头通电"，存档时保持断电。

## 根因找到（2026-10-01）：单 tick 内改动的"不同假玩家名"太多

1. 新世界，80 万条完全相同的简单命令（都写同一个分数），一条链一个 tick：30 万 / 50 万 / 65 万 / 80 万条 = 1.19 / 1.97 / 2.46 / 2.99 s/tick，**3.4–3.6 µs/条，完全线性，连跑几分钟也不变慢**。引擎没有"单 tick 执行量"的普遍上限。
2. 同一条链，命令改成轮流写 6 万个不同分数（`add r(i mod 60000) t5 1`）：**每 tick 482 秒**（SrvTime 482018），世界冻住，只能强退。
3. 5 万条命令的小链（基准：都写同一个分数，0.177 s/tick）：

   | 轮流写的分数 | 每 tick |
   |---|---|
   | 1,000 个不同名字，同一个记分项 | 0.201 s |
   | 5,000 个不同名字，同一个记分项 | 0.232 s |
   | **20,000 个不同名字，同一个记分项** | **34.8 s** |
   | 20,000 个不同名字，分散到 100 个记分项 | 10.3 s |
   | **20,000 个（名字，记分项）对 = 200 个名字 × 100 个记分项** | **0.221 s** |

**结论：代价取决于"一个 tick 里有多少个不同的分数持有者（假玩家名）的分数被改动"**，在 5,000 到 20,000 之间出现极陡的拐点（可能是某个固定容量，例如 16,384），和记分项数量、命令数量、命令类型都无关。T1M 一次前向改动约 6 万个不同的寄存器名，所以后半段爆炸；之前截断、分段、换命令都没有改变这个变量，所以都无效。

**修法**：`t44k/regmap.py`。把约 6.3 万个计算寄存器一一映射成（名字，记分项）对，名字只用 `q0`–`q255`，记分项 `v0`…`v245`；控制寄存器（run、pos、cur、fw、t*、out*、c* 快照等）保持原名在 `t4`。计算出的整数完全不变。
- 离线：T44K 尺寸 4 个提示词 64 次前向、训练版 T1M 1 个真实提示词 32 次前向，全部逐整数一致（`python -m t44k.check_staged t1m 1 --trained --regmap`）。
- 导出：`python -m t44k.export_staged <目录> t1m 32768 4 single --trained --regmap`（62,845 个寄存器 → 256 个名字 × 246 个记分项）。
- **实机（2026-10-01，新超平坦世界，带调试桥，原版按钮启动）**：同一训练版 T1M、同一提示词「中华」，**2.64 s/字**（第 5–21 字窗口；原来 12.6 s/字），**快约 4.8 倍**，32 字和最终状态全部逐整数一致。初始化 4.9 万条命令也从约 50 秒降到 0.6 秒（之前是同一个原因）。
