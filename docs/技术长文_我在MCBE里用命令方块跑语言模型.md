# 我在我的世界基岩版里，用命令方块跑真正的语言模型

> 作者：我（项目制作人）。代码和大部分实验由 Claude 完成，我负责方向、实机测试和关键判断。
> 时间：2026 年 9 月 28 日 – 10 月 1 日。平台：网易版我的世界基岩版（客户端约 v1.21.120），i5-13400F、RTX 4070 SUPER 12 GB、32 GB 内存、Windows。
> 本文偏技术，记录我们从第一个 6 千参数的小模型做到 125 万参数、并一路追查性能瓶颈的全过程。所有数字都是实测；没测成的东西我会直接写"没测成"。

---

## 摘要

- 我想回答一个问题：**只用原版命令方块和记分板，能不能在我的世界里运行一个真正的生成式语言模型？** 运行时不靠模组、脚本、外部程序，世界造好后所有附加包都能拿掉。
- 答案是能。三天里我们做了三代：
  - **v0.1.2**：6,272 参数，每字约 26 毫秒，零附加包运行通过；
  - **T44K / M6**：55,808 参数，用真实语料训练，做成了带键盘墙的独立世界，关掉所有组件后玩家自己按键就能生成、自检；
  - **T1M**：1,249,280 参数，6 层 Transformer，用中文维基训练，**整个前向是一条 87.2 万个命令方块的连锁链**，每个 tick 算一个字，约 11–13 秒一个字，游戏里的每个整数都和 Python 精确模拟一致。
- 核心技术是**三值权重 + 整数规范 + 拓扑编译**：每个非零权重编译成一条记分板加法或减法命令，零权重不生成任何东西。
- 现在的主要难题不是算力，而是一个还没查清的**单 tick 内超线性退化**：同一段命令单独跑很快，放在一个已经跑了 6 秒多的 tick 里就会慢几十倍。我们排除了七八种原因，但根因还没找到。

## 一、目标和约束

我给自己定的规矩：

1. **运行时只用原版**：命令方块、记分板、方块、原版命令。行为包里的 `.mcfunction`、Script API、网易 ModSDK 都不算，只能在开发期用来搭世界或调试。世界搭好后必须能移除所有附加包继续运行。
2. **不作弊**：token 编码、网络计算、选下一个字、连续生成都在游戏里完成，不能外面算好再查表。
3. **逐整数一致**：游戏里的每个整数都必须和外部的 Python 整数规范完全一样，"99% 一致"就算失败。
4. **语料干净**：训练数据不能来自闭源大模型（Claude、GPT、Gemini）的输出；可以用许可明确的公开数据，或者许可允许蒸馏的开源模型。

长期目标是摸清它的上限，看能不能走到 1 亿到 10 亿参数。

## 二、把我的世界当成一台计算机

| 计算机 | 我的世界里的东西 |
|---|---|
| 寄存器 | 记分板假玩家名，例如 `q3x17`、`K2p5d100`（记分项 `t4`） |
| 常量区 | 另一个记分项 `t4c`，例如 `c4096` |
| ALU | `scoreboard players operation A t4 += B t4`，以及 `-=`、`*=`、`/=`、`>`（取大）、`<`（取小） |
| 比较与分支 | `execute if score X t4 matches lo..hi`、`execute if score A t4 > B t4` |
| 程序 | 一条连锁命令方块链 |
| 条件跳转 | 一条"门"命令后面跟一串条件命令方块 |
| 时钟 | 游戏 tick（正常每秒 20 个） |
| 输入 / 输出 | 按钮、`tellraw` 聊天消息 |

这台机器的特点非常鲜明：**整数加减极便宜，乘除也有，但没有间接寻址**（不能用一个变量的值去选另一个变量），也没有循环，所有东西都要在编译期展开。

## 三、为什么是三值 Transformer

记分板最擅长的是"一个寄存器加上或减去另一个寄存器"。如果权重只能是 −1、0、+1：

$$
y_j = \sum_{i:\,w_{ji}=+1} x_i \;-\; \sum_{i:\,w_{ji}=-1} x_i
$$

那么一次矩阵乘就退化成一串加减：+1 编译成一条 `+=`，−1 编译成一条 `-=`，0 什么都不生成。T1M 里 60% 的权重是 0。

```mcfunction
scoreboard players operation q0x17 t4 = na0x3 t4
scoreboard players operation q0x17 t4 -= na0x9 t4
scoreboard players operation q0x17 t4 += na0x12 t4
```

每一行的第一个非零项用 `=` 开头，这样同一行被重复执行也不会越加越多。这一点后面会变得很重要。

我也考虑过 RWKV、Mamba 之类的结构，但在上下文只有 16–32 的时候，最大的开销是线性层，Transformer 的注意力并不贵，而且三值 Transformer 已经有成熟的训练方法（BitNet 一类的研究）。所以主线一直是三值 decoder-only Transformer。

## 四、整数规范：游戏和 Python 必须算出同一个数

`t44k/spec.py` 是唯一真相。游戏里能用的只有 32 位整数，所以整个网络从一开始就定义成整数运算，PyTorch 训练时也在同样的整数单位里做量化感知训练。

### 1. 不怕负数的四舍五入除法

不同平台对负数整数除法的取整方式不一样，所以每次除法都先加一个大偏移，让被除数永远非负：

$$
\operatorname{rdiv}(x, D) = \left\lfloor \frac{x + K\cdot D + \lfloor D/2 \rfloor}{D} \right\rfloor - K,\qquad K\cdot D \le 2^{30}
$$

```mcfunction
scoreboard players add xs t4 1073741826
scoreboard players operation xs t4 /= c4 t4c
scoreboard players remove xs t4 268435456
```

### 2. 整数 RMSNorm

$$
m = \operatorname{rdiv}\!\Big(\sum_i \operatorname{rdiv}(x_i,4)^2,\ d\Big),\quad
\mathrm{inv} = \mathrm{LUT}(m) \approx \frac{64\cdot 4096}{4\sqrt m},\quad
n_i = \operatorname{rdiv}(x_i\cdot\mathrm{inv},\ 4096)
$$

倒数开方用一张 48 档的几何分箱查找表代替，档位由训练后在真实数据上校准。

### 3. 整数注意力

q、k 先各除以 4，分数单位是 0.25 nat：

$$
s_j = \operatorname{rdiv}\!\Big(\sum_i \hat q_i \hat k_{j,i},\ \mathrm{ATTDIV}\Big),\qquad
w_j = \operatorname{round}\!\big(256\, e^{0.25(s_j - s_{\max})}\big),\qquad
a_i = \operatorname{rdiv}\!\Big(\sum_j w_j V_{j,i},\ \sum_j w_j\Big)
$$

exp 用查找表（每行一条 `execute if score dl t4 matches a..b run scoreboard players set w… t4 v`）。可变分母的除法同样加偏移，偏移乘数 KATT = 65536。

### 4. 残差、FFN、选字

$$
x \leftarrow x + \operatorname{rdiv}(W_o a\cdot M_O,\ R),\quad f=\max(0, W_1 n),\quad x \leftarrow x + \operatorname{rdiv}(W_2 f\cdot M_2,\ R)
$$

R = 65536，M_O、M_2、ATTDIV 每层单独学习、导出时取整。最后用三值 LM head 求每个字的分数，argmax 用严格的 `>`，分数相同选编号小的字。

| 常量 | 值 |
|---|---|
| 激活比例尺 S | 64 |
| RMSNorm 平方前缩放 PS | 4 |
| q·k 前缩放 QS | 4 |
| 倒数定点精度 INVR | 4096 |
| 注意力分数单位 | 0.25 nat |
| exp 表满权 | 256 |

## 五、编译：规范怎样变成命令方块

### 1. 门 + 条件块分派

记分板不能用变量当下标，所以"取第 cur 个字的 embedding""写第 pos 个 KV 槽"这类操作，每个可能的值都编译成一段命令，前面放一条门：

```mcfunction
execute if score cur t4 matches 135
scoreboard players set ee0 t4 -33      （条件块）
scoreboard players set ee1 t4 -17      （条件块）
……
```

门不成立时，后面的条件块全部跳过，每块只花约 1 微秒。

### 2. 因果跳过

注意力只算位置不超过当前 pos 的槽，同样用门：`execute if score pos t4 matches 5..` 后面跟一串计算第 5 个槽分数的条件块。平均能省一半注意力命令。

### 3. SSA 寄存器和"重复执行也算对"

网易的循环命令方块断电后还会多跑 1–2 个 tick，这是第一版自检 FAIL 的原因（62 个整数对不上，聊天栏多出「萝」「里」两个字）。之后我们定下三条规矩：

- **每个阶段写自己的寄存器**（SSA），任何一段被重复执行，结果都一样；
- 链首先锁存 `live = run`，只有锁存为真时才推进 pos、输出字、判断停机；
- 停机时把最终状态拍成快照（`c*` 寄存器），自检只比对快照。

### 4. 敏感词过滤

网易会**静默吞掉**含有屏蔽词的命令，不报错也不反馈，命令方块、函数、聊天栏手敲的都一样。第一次是记分项叫 `sb`，整个实验包没反应，查了很久。后来发现连记分板名字也会被过滤：带 `j8` 的、`bl`，还有含某些特定数字组合的名字都不行，而且过滤会忽略分隔符去看数字。对策：
- 下标一律用字母分隔，比如 `K0p7d31`；
- 构建时跑 `netease_lint` 检查；
- 上机前在游戏里把全部寄存器名（T1M 有 6.3 万个）逐个试写一遍。

告示牌文字另有一层过滤：「泽」「近」写不上去，拼音 `jin` 也不行，但同样的字放在 `tellraw` 里正常。

## 六、布局：命令方块怎么摆

- **蛇形连锁链**：一层一层往上铺，每层蛇形走完。T1M 单链用 192 × 63 的底面，一共 73 层。
- **条件块看的是"几何上身后"的方块**，不是链上的前一个。蛇形转弯处每次有两个格子不满足这个关系，别的字的 embedding 段就被误执行了。修法 `regate()`：在转弯格放一份当前段门命令的无条件副本。世界模拟器也按几何规则判断，关掉修法能复现这个错误。
- **链头**：需要红石的循环命令方块，旁边放一个红石块，就每个 tick 跑一次完整前向；`run` 变 0 时链尾自己拆掉红石块。
- **链长**：`gamerule maxcommandchainlength` 默认 65535，**可以调到 1,000,000**。实测一条 10 万块的链能完整执行，T1M 的 87 万块单链也正常运行。
- **放得远**：渲染距离内有大量命令方块时我的帧率只剩 15。所以模型核心都放在几千到几万格外的常加载区，身边只留键盘。

## 七、平台实测（E0–E4）

| 实验 | 结论 |
|---|---|
| E1 实体选择器批量运算 | 选择器命令每条固定约 0.31 ms，每命中一个实体再加约 2.2 µs，还会随世界实体总数变慢。**淘汰**。另外 3000 个盔甲架会直接把游戏卡死。 |
| E0 链长 | 每 tick 4 万条命令正常；多条链不会并行加速。 |
| E2 `/structure load` 换页 | 换页 1678 次全部正确，但加载一个命令方块约 52–110 µs，是执行的约 20 倍。 |
| E3 NX 分叉（我带进来的思路） | `execute rotated as @e[…] positioned ^ ^ ^d` 嵌套，用多个朝向不同的实体当方向模板，指数展开执行上下文。网易版能用，但每个叶子 3–5 µs，不能加速计算；在方块上做三值矩阵乘结果正确，但慢约 15 倍。 |
| E4 常驻上限 | 空闲命令方块每 tick 空转约 0.1–0.24 µs，内存约 2.5 KB/个。**内存是第一道墙**：普通电脑大约能常驻 100–300 万个命令方块。 |

由此定下的路线：**一个非零权重 = 一条命令，命令方块常驻在远处，放不下时再考虑换页或用普通方块存权重。**

## 八、三代模型

### v0.1.x

1 层、d=16、2 头、词表 128、上下文 8，6,272 参数，numpy 手写反向传播训练。每字约 26 ms，每秒 20 字时 TPS 不掉。移除附加包后 `/function` 报未知函数，自检照样 PASS。

### T44K 与 M6

- 2 层、d=32、4 头、FFN 112、上下文 16。先用随机权重验证引擎：24 个提示词、384 次前向逐整数一致。合并成单链后，每字从 0.6 秒降到 0.14 秒。
- **语料**：我选了 DeepSeek 官方 API 当老师（它的协议允许用输出训练其他模型），并要求脚本里放随机的请求间隔、退避和每小时上限。320 字的词表只能用上 30% 的句子，我同意扩到 512 字，再用限定字表跑第二轮，最后 3.24 万句。
- **训练**：PyTorch 显卡版，整数单位里做三值量化感知训练（直通估计取整、按绝对值阈值三值化），约 15 分钟。下一个字准确率 31.4%（浮点）/ 31.0%（整数）。
- 游戏里第一次说出了像样的话：石镐→挖石头、熟牛→肉能回血、我挖→到红石矿、洞里→见僵尸、骷髅→射箭。
- **M6 独立世界**：远处放核心、常开轮询器（把按键追加到提示词缓冲，自检时比对 50 个整数）、初始化链；我身边是 508 个字键 + 五个功能键的键盘墙。我一试就发现**串线**：按钮直接挂在命令方块上会把相邻命令方块一起激活。改成"按钮 → 石头 → 命令方块"后修好。最后我关掉所有组件，手动按键生成、自检，全部 PASS。

### T1M

- 6 层、d=128、8 头 × 16、FFN 384、词表 1024、上下文 32，**1,249,280 参数**。
- **引擎泛化**：尺寸可配置；编译器能把一次前向切成很多"自成一体"的单元（每个寄存器只由一个单元写），可以拆成多条链；回归检查保证 T44K 编出来的命令逐字节不变。
- **语料换成中文维基**（CC BY-SA 3.0，人写文本）。长句按逗号切段，常用 1024 字以外的生僻字记为 `<UNK>`，只作为上下文，不当训练目标，也不会被生成。最后 142 万条、2770 万字。
- **训练**：8 万步 × batch 512，约 63 分钟；验证损失 4.06，下一个字准确率浮点 27.4% / 整数 27.7%。后来测出 `torch.compile` 能让训练快约 2.1 倍（47 → 22 ms/步），TF32 没有收益。
- 游戏里 4 个真实提示词，**每个字、每个整数都和规范一致**。例句：是建→筑物的一个建筑，包括一个小型的建筑……；这本→书的记载，这些文字是一种说法……。贪心解码下会绕圈重复。
- **速度**：分 15 段接力时每字 18.9 秒；改成一条 87 万块的单链、每 tick 算一个字后约 11–13 秒（游戏里 SrvTime 约 12000–15000 毫秒）。

## 九、验证体系

每一层都要逐整数一致，才往下一层走：

1. **Python 整数规范**：唯一真相，带数值范围守卫；
2. **命令文本解释器**：一条一条执行真正的命令文本，比对每个中间整数，截断和向下取整两种除法语义都要过；
3. **逐 tick 世界模拟**：模拟条件块的几何规则、脉冲链头延迟、循环链头断电后多跑的 tick；
4. **游戏内试写全部名字**；
5. **实机逐 token、逐整数比对**；
6. **拔掉所有组件后自检**，另外故意改错一个整数做对照，确认会报 FAIL。

## 十、性能之谜：一次漫长的排查

按局部测速，T1M 每字约 57.5 万条有效命令 × 3–5 µs ≈ 2–3 秒，再加约 30 万个被跳过的条件块（约 1 µs/块），也就 3 秒左右。实测却是 11–13 秒。下面是我们一步步排查的过程。

### 1. 先排除的东西

| 怀疑 | 测试 | 结果 |
|---|---|---|
| 链太长 | 同一条简单命令分别放在 2 万 / 10 万 / 30 万长的链里 | 3.3 / 3.9 / 4.4 µs/条，只是轻微上升 |
| 命令各不相同 | 30 万条只改数字的不同命令 | 约 2.6 µs/条 |
| 真实命令组合 | 从 T1M 链里截出 7 万条单独跑 | 约 2.7 µs/条 |
| 记分项名字太多 | 6.3 万个名字 vs 几个名字 | 没区别 |
| 数值变化、大幅跳动、条件结果翻转 | 专门的基准 | 都是 4–6 µs/条 |
| 被跳过的条件块 | 10 万个 | 约 1 µs/块 |

### 2. 第一份深度研究：TrackOutput

我把问题交给 GPT 做深度研究。它的首要猜测是命令方块的"记录输出"（TrackOutput / LastOutput）让方块实体不断被标记修改。我们用 ModSDK 把 87 万个方块全部关掉：**整句平均 11.3 → 11.1 秒，基本无效**。结果仍然逐整数一致。

顺带踩到一个坑：用 `SetBlockEntityData` 写回方块数据时，游戏会按里面的 `LPCommandMode / LPCondionalMode / LPRedstoneMode` 重设方块类型；用 ModSDK 放下的方块这三个字段有时是 0，写回后一段连锁块变成了"脉冲、无条件"，链从中间断掉。只能把整条链重放一遍，并显式写对这三个字段。

### 3. 截断二分：慢集中在一小段

把真实链在不同位置截断，数值冻结，测每 tick 耗时：

| 截到 | 每 tick |
|---|---|
| 60 万块 | 3.6 s |
| 第 5 层注意力结束（76.6 万块） | 5.4 s |
| **再往后 2.9 万块** | **22.4 s** |

约 17 秒集中在第 5 层中间的 2.9 万个方块。同样结构的第 4 层完全正常；把这 2.9 万块原样复制到别处单独跑，也很快。

### 4. 第二份深度研究：分段执行

GPT 的第二份报告推测是"单个 tick 内的累积"，建议把一次前向拆到多个 tick。我们实测（同一提示词，结果都逐整数一致）：

| 版本 | 每字 |
|---|---|
| 单链 | 11.1–11.3 s |
| 拆 2 段 | 16.6 s |
| 拆 6 段 | 约 19.6 s |

**拆开反而更慢**。每段之间要等 2 个 tick 接力，而且拆开后每段并没有变快：6 段版里一段 15 万条命令扣掉空闲还要约 2.8 s，同样的命令在单链里只要约 1.1 s。

### 5. 对照实验 C：问题在"之前跑了多少"

把那 2.9 万块当作"探针"固定在原位，只改执行从哪里开始（临时把某一块换成常开的循环链头）：

| 执行范围 | 每 tick |
|---|---|
| 只跑探针 | 0.79 s |
| 第 5 层开头 → 探针结束 | 1.30 s |
| 第 4 层开头 → 探针结束 | 2.25 s |
| 链头 → 探针开头 | 6.4 s |
| **链头 → 探针结束** | **38.6 s** |
| 跳过 embedding 段（13.7 万块）→ 探针结束 | 39 s |

结论：
- **探针本身不贵**。只有在同一个 tick 里前面已经跑了很久或很多以后，探针末尾的 1.45 万块（第 5 层 FFN 上投影的后半）才会爆炸；
- 跳过 13.7 万个大多被跳过的条件块不影响结果，所以不是"遍历过的方块数"；
- 长 tick 里游戏进程内存几乎不变（±30 MB），不是内存累积。

### 6. 测量本身也会拖慢

同一个配置（链头 → 探针结束）：
- 开着我们 0.05 秒一次的测速定时器：**38 秒/tick**；
- 不开任何定时器、只用一个每 tick 加 1 的命令方块计数：**11.5 秒/tick**，我在游戏里看到的 SrvTime 约 12000。

所以用定时器测出的断崖数值被放大了。断崖真实存在，但幅度要以无定时器的数据为准。以后只用"命令方块计 tick"和我读 SrvTime 来测。

### 7. 没做成的：零附加包对照

最关键的一步是看去掉附加包、去掉 Python 层之后，这个断崖还在不在、T1M 每字能不能快很多。我们试了三次，都没做成：

- 第一次：链头通着电存档，移除附加包后进图，两次都在加载快结束时闪退。推测是加载期间就开始跑 12 秒的长 tick。
- 第二次：改用原版石头按钮启动（存档时链是断电的）。带桥时测得 **12.6 秒/字**，32 个字全部逐整数一致。但存档时常加载区还开着，下次进图在加载界面卡了 10 分钟以上，因为游戏要先把那 48 个塞满命令方块的区块全部读完。
- 第三次：我们在存档前移除了常加载区，准备零附加包重进，但开发者启动器崩了。
- 第四次：存档找回来了。移除全部组件后进图，按原版按钮生成，SrvTime 稳定在**约 11300 毫秒，也就是约 11.3 秒一个字**；带调试桥时约 12–12.6 秒。**附加包和 Python 层只占约 10%。**

### 8. 目前的判断

- 慢的根本原因是**同一个 tick 里跑得足够久或足够多以后，后面的命令突然变贵**，而且这种退化在分段接力时似乎会跨 tick 延续。
- 已经排除：TrackOutput、命令文本（包括敏感词过滤）、链长本身、记分项名字多、数值变化、条件翻转、内存累积、遍历方块数。
- 零附加包对照显示附加包 / Python 层只带来约 10% 的差别，所以**慢和断崖主要来自游戏引擎本身**。剩下的嫌疑是引擎内部某种随执行量累积的逐 tick 簿记，需要换角度继续查。

---

### 9. 找到了：问题是"一个 tick 里改了多少个不同的假玩家"

最后用最干净的实验收尾：新世界里只放一条 80 万条完全相同的简单命令（都写同一个分数），**每 tick 3 秒，完全线性，没有任何断崖**。然后只改一件事，让命令轮流写 6 万个不同的分数，**每 tick 变成 482 秒**，世界直接冻住。

再用 5 万条命令的小链细测：

| 轮流写的分数 | 每 tick |
|---|---|
| 都写同一个分数 | 0.18 s |
| 1,000 个不同名字 | 0.20 s |
| 5,000 个不同名字 | 0.23 s |
| **20,000 个不同名字（同一个记分项）** | **34.8 s** |
| **20,000 对 = 200 个名字 × 100 个记分项** | **0.22 s** |

**根因：一个 tick 里，被改动分数的"不同假玩家名"一旦超过几千到两万个，之后每次改动都会变得极贵；而记分项有多少个根本无所谓。** T1M 一个字要改动约 6 万个不同的寄存器名，所以后半段爆炸。之前的截断、分段、换命令都没碰到这个变量，所以都无效。

**修法很简单**：把约 6.3 万个寄存器换成"256 个名字 × 246 个记分项"的组合，每个寄存器仍然独立，算出来的整数完全一样。离线逐整数验证通过后上机：**同一个模型、同一句话，从每字 12.6 秒降到 2.64 秒，快约 4.8 倍**，32 个字全部逐整数一致。顺带，初始化 4.9 万条命令也从约 50 秒降到 0.6 秒。

查了三天的"超线性之谜"，答案藏在一个谁都没注意的变量里：**不是算得多，而是名字多**。

## 十一、规模上限的判断

- **算力**：每个参数约 0.4 条命令，每条 3–5 µs。理想情况下 1M 参数约 2 秒/字，10M 约 20 秒，0.1B 约 3 分钟，1B 约 30 分钟。
- **内存才是先撞上的墙**：一个命令方块约 2.5 KB。87 万块已经让游戏进程到 5 GB 左右；常驻上限大约是 200–300 万个非零权重，即约 5–7M 参数（60% 为零时）。
- **再往上必须把"参数存储"和"命令方块"分开**：候选是用普通方块存三值权重（几乎不占内存、不空转），再用一个固定的读取程序（`execute if block`）配合 `/clone` 分页读取；也可以用混合专家让每个字只激活一小部分参数。这些都还没实测。
- **下一代模型**的设计方向是深而窄、K/V 只保留一组、分解词表、75–85% 零权重（例如约 566 万参数、12 层、d=224、词表 1536），让参数量翻几倍、每字的命令数只增加两三倍。

## 十二、工程教训

1. **整数规范是唯一真相**，每一层都要逐整数验证。
2. **先量再定**：很多直觉都被数据推翻过，比如"每 tick 命令太多"其实是 `sb` 被过滤，"TrackOutput 拖慢"实测无效，"分段能变快"实测更慢。
3. **重复执行也要算对**：网易的命令方块会多跑，寄存器每段只写一次，控制加锁存，停机拍快照。
4. **大结构放远处**，身边只放键盘。
5. **游戏要保持在前台**：按 ESC 或窗口失焦，tick 就会暂停，调试桥会超时，测速会被污染。
6. **不要在运行中一次删除几十万个命令方块**：87 万块时整个世界冻住 10 分钟以上。换版本时搭在新空地，再移除旧的常加载区；或者直接开新世界。
7. **不要让大命令链通着电存档**，进图时会在加载期间跑长 tick 导致闪退。用原版按钮启动。
8. **存档时不要让装着几十万命令方块的常加载区开着**，否则进图要先把它们全部加载完，会在加载界面卡很久甚至卡死。进图后再手动加常加载区。
9. **用 ModSDK 改造命令方块要小心**：把连锁块原地改成常开循环块不会开始 tick，要先设成空气再放；写方块数据时要显式写对三个模式字段。
10. **游戏开着大世界时不要跑训练**：有一次内存被吃到只剩 4 GB，我的电脑差点被拖崩。
11. **测量工具会影响被测对象**：长 tick 里的定时器能把 11.5 秒拖成 38 秒。
