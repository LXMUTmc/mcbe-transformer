# E3 结果：NX 分叉（共轭二分 / N 叉树）与方块 ROM

2026-09-29，网易 MCBE，i5-13400F，调试桥在游戏里直接测。

## NX 技巧（用户提供）

在同一位置放 k 个朝向不同的实体作为"方向模板"。`execute rotated as @e[tag=…]` 让一条命令按每个实体的朝向各执行一次，再配合 `positioned ^ ^ ^d`，同一个局部位移会落到不同的世界坐标。嵌套 n 层就得到 k^n 个执行上下文：k=2 叫共轭二分，k>2 叫 N 叉树。**网易版实测可用**：嵌套 1/4/8 层分别得到 2/16/256 个叶子，数量完全正确。

## 每个叶子的成本

通过 `SetCommand` 执行单条 NX 命令并计时。单条命令本身的开销只有约 0.008 ms，可以忽略。

| 配置 | 叶子数 | µs/叶子 |
|---|---|---|
| 二叉，只分叉，叶子做一次加法 | 1K–64K | 7.7 |
| 二叉，每层加 `positioned ^ ^ ^0.5` | 1K–64K | 10.0 |
| 二叉，位移 + 叶子读一个方块 `if block` | 1K–64K | 11.2 |
| 16 叉，位移 + 加法 | 4K / 64K | 4.5 |
| 16 叉，位移 + 只读方块 | 4K / 64K | 5.5–5.7 |
| 64 叉，不位移 + 加法 | 4K / 262K | **3.0** |
| 64 叉，位移 + 加法 | 4K / 262K | 4.2–5.3 |

- 二叉树的内部节点数约等于叶子数，每个内部节点都要求值一次选择器（约 7 µs），所以二叉很慢。k 越大，平均到每个叶子的选择器开销越小，最后剩下约 3 µs 的底价（生成旋转上下文），每层位移再加 1–2 µs。
- **NX 的叶子成本（约 3–5 µs）和一条常驻命令方块执行一次（约 4.3–5.6 µs）差不多，所以在"算"上不会更快。** 而且所有叶子执行的是同一段命令文本，记分板名字是写死的，没法让不同叶子加到不同的 y_i 上。要用它算矩阵乘，只能"一条 NX 命令负责一个输出 y_i、叶子遍历 d_in 个位置"，用 popcount 的方式：权重方块和输入方块同时匹配才计数。输入是多位整数时要按二进制位拆开逐位做，成本乘以位数。

## 加载成本（由命令方块驱动 `structure load`，按真实 tick 计时）

同一位置每 tick 交替加载两份内容不同的结构。

| 内容 | 每 tick | 每个方块 | 其中 `structure load` 当场完成的部分 |
|---|---|---|---|
| 16128 个命令方块，加载后不执行 | 845 ms | **52 µs** | 约 10.7 µs（其余约 40 µs 被推迟到同一 tick 后半段） |
| 16128 个命令方块，加载后执行一次 | 1002 ms | 52 µs + 首次执行 9.7 µs/条 | — |
| 同一页常驻、每 tick 执行（不加载） | 93.5 ms | 执行 5.6–5.8 µs/条 | — |
| 32768 个普通方块（羊毛 ROM） | 212 ms | **6.5 µs** | 约 5.2 µs |

- **更正 E2 的解释**：换页贵在**加载命令方块本身**（约 52 µs/个，主要是被推迟的方块实体处理），不是命令解析。新方块第一次执行只比常驻多约 4 µs/条。E2 推算的约 110 µs 和这里同一个量级（E2 的页面命令更长，所以更贵）。
- **普通方块的加载比命令方块便宜约 8 倍。**
- 注意：用 `SetCommand` 给 `structure load` 单独计时，会漏掉被推迟的那部分。加载成本必须按整个 tick 的真实时长来量。另外调试桥的 `AddRepeatedTimer(0.0)` 在服务端很忙时一个 tick 可能被调用多次，不能拿它的调用次数当 tick 数；tick 数要用命令方块自己计数。

## 实测 NX 方块 ROM 矩阵乘（"低位激活"路线，2026-09-29，E4 世界）

- **布局**：16 个朝向每次相差 22.5° 的盔甲架；两层 NX，外圈半径 26、内圈半径 3.25，得到 256 个叶子。已验证 256 个叶子两两落在不同的格子里，离格子边界至少 0.11 格，抽查 16 个叶子的位置全部和游戏一致。朝向 θ 的前进方向是 (−sin θ, cos θ)。
- **权重 ROM**：每个输出占一层（绿色羊毛 = +1、红色 = −1、空气 = 0）。**输入平面**单独一层（三值）。
- **每个输出 4 条 NX 命令**：权重和输入各检查一个方块，按 (+,+) 加、(−,−) 加、(+,−) 减、(−,+) 减。
- 64×256，50% 非零权重，三值输入（50% 非零）：**64 个输出和 Python 全部一致**；耗时 508 ms，**每个权重位置 31 µs，每个非零权重 63 µs**。拓扑编译是 4.3 µs/非零权重，**计算慢约 15 倍**。
- 慢的原因：零权重也要扫描；每个叶子只能执行一个动作，所以三值 × 三值要 4 遍；每个叶子的分叉本身就要约 5–7 µs。改成二值输入（2 遍）、64 叉等优化后，估计每个位置最低约 5–8 µs，仍然比拓扑慢。
- 唯一优势是存储：普通方块不空转、几乎不占内存，整个模型可以以方块形式常驻，不用换页。但 0.1B 下每个字约 10–50 分钟，不比"拓扑编译 + 换页"（90% 为零时约 10 分钟）更好，而且需要二值或三值激活。**结论：不作为主线**，保留给"存储是唯一瓶颈"的特殊层再考虑。

## 结论

1. **NX 不能加速计算**，每个叶子约 3–5 µs，和常驻命令一样。但它是目前唯一能"一条命令扫一大片方块"的办法，适合读取方块 ROM，以及批量启动子链（叶子执行 `setblock … redstone_block`）。
2. **方块 ROM + NX 的对比**：要换页的模型里，每个权重每次读取约 6.5 µs（加载）+ 约 5 µs × 位平面数 × 2（NX 读取，正负权重各一次）。零权重也要读。只有在权重稠密、激活位数很低（二值或三值激活）时，才可能比"命令方块换页"（每个非零权重约 52–110 µs 加载 + 5–10 µs 执行）划算。在 90% 稀疏、8 位激活时反而更慢。
3. **最关键的还是常驻**：常驻执行 5.6 µs/条，换页要 50–110 µs/条。下一步应该测常驻的上限：几百万个命令方块放在常加载区块里时，空闲开销、内存、存档大小，以及启动时能不能正常加载。
4. 可以留作后续方向：用二值或三值激活加 popcount 的模型结构（每层只写一次输入平面，用 NX 在方块 ROM 上做点积）。这需要在模型训练里验证质量损失，暂不作为主线。
