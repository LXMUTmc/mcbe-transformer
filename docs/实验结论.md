# 实验结论：哪些路走通了，哪些没走通

所有数字都来自实测：网易 MCBE 约 v1.21.120，i5-13400F + RTX 4070 SUPER + 32 GB 内存，调试桥真实时钟计时；离线部分用本仓库的脚本。详细记录在 `docs/E0…E6_*.md`、`docs/大规模路线.md`、`docs/HANDBOOK.md`。

## 一、走通了的（现在的主线）

| 做法 | 效果 |
|---|---|
| 三值权重拓扑编译：一个非零权重一条命令 | 约 4.3–5.6 µs/条，是所有试过的计算方式里最快的 |
| 整数规范 + 量化感知训练 | 游戏和 Python 逐整数一致；整数模型比浮点模型的下一个字准确率低 0–2 个百分点（T10M：45.5% 对 47.5%） |
| 整次前向放进一条链、一个 tick | `maxcommandchainlength` 能调到 4,000,000，310 万块的链一个 tick 跑完；分阶段接力每阶段要 2 个 tick，更慢 |
| **regmap**（最重要的性能发现） | 一个 tick 里改动的不同假玩家名超过约 5,000–20,000 个后，每次改动都变得极贵（5 万条命令：5K 个名字 0.23 s/tick，2 万个名字 34.8 s/tick）。和记分项数量无关。把寄存器映射成 256 个名字 × 很多记分项后，T1M 从 12.6 s/字降到 2.64 s/字 |
| 矩阵公共子式消除（CSE） | 贪心带符号配对，矩阵乘命令少 40%（×1.68），整数结果不变 |
| 嵌入表打包 | 3 个 INT8 值装进一个分数，T1M64 少 25% 的方块 |
| 断链器（`repeat_brk`） | 循环链头断电后多跑的 1–2 tick 不再算完整前向，每次生成省 7–14 秒 |
| 解码规则 | "出现过的字扣分 + 标点后不接标点"：复读率 0.213 → 0.022 |
| 对话：去万能回答 + 每轮清空出现过的字 | 万能回答 73–83% → 27–30% |
| 对话：从 LCCC 挖问答（评委模型 PMI 打分） | 在去万能回答的基础上再加 43 万组相关问答，一起训练 16 万步 |

## 二、没走通的

| 尝试 | 结果 | 为什么不行 |
|---|---|---|
| 实体选择器并行（一条命令作用于一批实体） | 每条固定 0.31 ms，每命中一个实体再加 2.24 µs，还随世界实体总数线性变慢 | 比一条一条算慢得多（E1） |
| NX 分叉（`execute rotated as` 嵌套出大量上下文） | 能用，每个叶子 3–5 µs | 和常驻命令一样贵；所有叶子执行同一段命令文本，写不到不同的寄存器（E3） |
| 方块 ROM + NX 矩阵乘 | 结果正确 | 每个非零权重 63 µs，是拓扑编译的约 15 倍（E3） |
| `/structure load` 换页 | 1678 次换页全部正确 | 约 52–110 µs/命令方块，是执行成本的约 20 倍。主要花在加载方块实体上，不是解析命令（E2、E3） |
| 分段扫描（把一条长链拆成几段） | 逐整数一致 | 2 段 16.6 s/字、6 段 19.6 s/字，都比单链 11.1 s 慢 |
| 脉冲链头自己重新触发自己 / 看门狗重新触发 | 网易版里第一次前向后就停住 | 链头像是"记住了已通电"；改用断链器 |
| 记分板细调（名字数、比例、写入顺序、各种运算） | 都在 10% 噪声以内 | 没有空间；只知道 `execute if … run` 贵 50%（E6） |
| 蒸馏（学生学老师的概率分布） | 39.8% 对不蒸馏的 39.9% | 提升主要来自语料本身，蒸馏几乎没贡献 |
| 更稀疏（更多零权重） | 60% 零：43.6%；70% 零：42.7%，命令 −17.5%；75% 零：42.1%，命令 −27% | 70% 是还算划算的折中，再稀疏质量掉得明显 |
| 跨层共享权重（12 层共用 6 套） | 准确率 38.4% → 39.1%，验证损失 2.981 → 2.961（T4M，4 万步） | 质量只涨 0.7 个百分点，每个字的计算量却翻倍；游戏里命令方块按层展开，共享省不了方块 |
| RMSNorm 查找表加精度 | 48 档 27.79%、精确值 27.84%、96 档 27.67% | 噪声以内 |
| 方块记忆里放 n-gram 统计（盔甲架当指针，读羊毛方块） | 读取能用：0.82 ms 一次，结果正确 | 离线评估的真实收益只有 +0.4–1.7 个百分点（见下） |

### n-gram 方块记忆的教训

- 先前测出"加 n-gram 统计表能 +4 个百分点"，后来发现大部分是**背答案**：对话验证集只有 17% 是训练集里没见过的句子，其余在 LCCC 里几乎原样出现过。微博上的转发和重复太多。
- 只看没见过的句子，真实收益如下（下一个字准确率提高的百分点）：

| 表里的上下文数 | 新句子 | 见过的句子 |
|---|---|---|
| 2284 万（全部） | +1.7 | +5.5 |
| 500 万 | +1.3 | +3.4 |
| 200 万 | +0.7 | +1.4 |
| 100 万 | +0.4 | +0.9 |

- 游戏里放得下的规模大约是 200 万个上下文，收益约 +0.7。作为对比，模型从 T7M 加大到 T10M 是 +1.5。
- **教训**：评估任何"记忆"类方法时，先查验证集和训练集有没有重复。

## 三、天花板在哪里

| 资源 | 实测 | 对应的极限 |
|---|---|---|
| 内存 | 约 2.5 KB/命令方块 | 32 GB 的电脑大约能放 310–400 万块，也就是约 1000–1300 万参数 |
| 时间 | 约 5 µs/条命令，加上空转约 0.27 µs/块/tick | T10M 每个字约 200 万条命令，约 11 秒 |
| 渲染 | 渲染距离内的命令方块非常卡 | 大结构一律放在远处的常加载区 |

如果升级到 64 GB 内存，大约能放 2000 万参数，但每个字要约 20 秒。再往上，常驻命令方块这条路就走不动了。

规模和质量（同数据、8 万步，对话验证集损失）：T4M 3.640 → T7M 3.560 → T10M 3.492，仍在稳定下降。也就是说，**限制质量的是游戏的内存和速度，不是训练方法**。

## 四、网易版的坑（都踩过）

- **敏感词过滤会静默吞掉命令**：命令文本、记分项、假玩家名都受影响，不报错。被拦过的包括 `sb`、`bl`、`…j8`、`qq`，以及含某些特定数字组合的名字等。名字下标用字母分隔；上机前把所有名字在游戏里试写一遍。
- **告示牌**另有一层过滤：`泽`、`近`、`jin` 写不进告示牌，但 tellraw 里正常。
- **条件连锁块**判断的是"几何上身后"的方块，不是链上的前一个。蛇形转弯处要特殊处理。
- **按钮挂在命令方块上**会强充能该方块，连带触发相邻的命令方块。所以按钮挂在石头上，命令方块放在石头后面。
- **常加载区**：在已加载的大结构上加第二个、或改名的常加载区，会重新加载全部区块，游戏冻住十几分钟。开着常加载区存档，下次进世界会卡在加载界面。
- 在运行中的世界里用 `/fill` 删除上百万个命令方块，游戏会冻住 10 分钟以上。要重建，就换新区域或新世界。
- 窗口在后台、或者打开了暂停菜单，tick 会停住，调试桥会超时，测速也会被污染。
- 附加包和 Python 层只占约 10% 的时间，慢主要来自游戏引擎本身。
